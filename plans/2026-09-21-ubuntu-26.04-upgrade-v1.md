# Plan: Upgrade `docker.base` and `docker.loghi-tooling` to Ubuntu 26.04

- Date: 2026-09-21
- Version: v1
- Status: **implemented 2026-09-21** - both images built and verified on 26.04. Two deviations from the original index, both documented: **D1** useradd UID-1000 fix (tooling Dockerfile rationale) and **D2** slf4j-api 2.0.18 pin in `loghiwebservice/pom.xml` (after Step 8)

## 1. Architecture overview

`docker.base` is a build+runtime image: it compiles OpenCV 4.14.0 from source (cloned fresh from GitHub by `buildAndInstallOpencv.sh`), installs the jar/JNI lib under `/usr/local/share/java/opencv4/` and `/usr/lib/jni/`, then strips build tooling via a big `apt-get remove`. `docker.loghi-tooling` extends `docker.base`, installs Maven + JDK, builds `prima-core-libs` -> `langident` (fresh GitHub clone) -> `loghi-tooling` (copied in by `buildImage.sh`), and strips the JDK, leaving a Java runtime plus all OpenCV runtime libs for the Dropwizard web service on port 9006.

The 26.04 port is therefore: (a) swap focal-only apt package names in both Dockerfiles, (b) replace Java 11 with Java 17 (forced by Dropwizard 5.0.2's Java-17 baseline in `loghiwebservice`), (c) align the stale OpenCV 4.12.0 references in the tooling Dockerfile/poms to the 4.14.0 that `docker.base` already builds, (d) rewrite the post-build `apt-get remove` list, whose focal-only names (`gcc-9`, `cpp-9`, `libdc1394-22-dev`, `libopenblas-base`) hard-fail `apt-get remove` on 26.04 (atomic operation: one unknown name fails the whole cleanup step).

Rationale for every delta vs. the current file (all names verified against 26.04 apt):

- `FROM ubuntu:26.04` - the actual goal.
- Install list: `qt5-default` -> `qtbase5-dev` (qt5-default has **no candidate** on 26.04); `libatlas-base-dev` **deleted** (gone from 26.04; OpenCV falls back to OpenBLAS, `libopenblas-dev` stays); `libtbb2` **deleted** (gone; `libtbb-dev` pulls `libtbb12`); `libdc1394-22-dev` -> `libdc1394-dev` (22-series not in the 26.04 index); `libopenblas-base` **deleted** (not in index; `libopenblas-dev` stays); `default-jdk` -> `openjdk-17-jdk` (see Q4 in section 7); **added** `libstdc++6 libgcc-s1` (insurance: keeps the C++ runtime that `libopencv_core.so.414` needs explicitly installed - in the current image they survive only by accident).
- Remove list: same renames as the install list; `default-jdk`, `gcc-9`, `cpp-9`, `default-jre*`, `openjdk-11-*` **deleted** - `gcc-9`/`cpp-9`/`libdc1394-22-dev`/`libopenblas-base` are not in the 26.04 index, which would make the *entire* atomic `apt-get remove` fail with "Unable to locate". The JDK/toolchain chains are removed explicitly by real 26.04 names: `openjdk-17-jdk openjdk-17-jdk-headless openjdk-17-jre openjdk-17-jre-headless` (17.0.20+8-1~26.04) and `g++-15 gcc-15 cpp-15 libstdc++-15-dev libgcc-15-dev` (15.2.0-16ubuntu1).
- Typo fix: `rm -rf rm -rf /var/lib/apt` -> `rm -rf /var/lib/apt`.
- **ldd gate (new):** fails the build if any OpenCV runtime lib is unresolved, *except* `libtbb.so` - the base is deliberately TBB-less by design (today: `libtbb.so.2 => not found`; the tooling image supplies the TBB runtime). On 26.04 OpenCV links `libtbb.so.12` from `libtbb12`.

Pitfalls (all verified):

- `apt-get remove` is atomic: every name must exist in the 26.04 index. Removing a package that *is* in the index but not installed (e.g. a no-candidate package such as `qt5-default` or `libtbb2`) is exit 0 - safe. Removing a name not in the index at all (`gcc-9`, `cpp-9`, `libdc1394-22-dev`, `libopenblas-base`) is a hard failure - hence they are out of the list.
- `apt-get remove` does **not** remove a package's dependencies (only reverse deps), and in this image `apt autoremove` is effectively a **no-op** - verified: `apt-get -s autoremove` inside the current `docker.base:latest` reports "0 to remove" because `/var/lib/apt` (with the auto/manual extended states) is deleted before it runs. Therefore the remove list must be exhaustive (it is). Consequence: runtime libs (ffmpeg, tbb12, protobuf, `libavutil60`, ...) stay in the base image, exactly like today's ~1.7 GB image; the tooling's explicit installs are then idempotent.
- `opencv_version` will **not** run in the base image (it links `libopencv_core` -> TBB missing). Expected; it is a tooling-image test only.

## 5. Edge cases and error handling

1. **Atomic `apt-get remove`** (highest-risk item): one name missing from the 26.04 index fails the whole cleanup RUN. Verified absent from the index: `gcc-9`, `cpp-9`, `libdc1394-22-dev`, `libopenblas-base` - all removed from the list. Verified safe: no-candidate/no-install names like `qt5-default`, `libtbb2` exit 0 - still removed from the list for cleanliness. If the build fails in the cleanup RUN with `E: Unable to locate package X`, remove/replace just `X` (the ldd gates still protect the result).
2. **`autoremove` is a no-op** in this design (extended states lost after `rm -rf /var/lib/apt` - verified: 0-to-remove simulation in the current image). Never rely on it; the explicit remove lists are complete. If image size balloons vs ~1.7-2.2 GB, diff `dpkg -l` against the lists.
3. **TBB soname jump** `.2` -> `.12`: anything still referencing `libtbb2` will silently miss the library. Both Dockerfiles use `libtbb12`/`libtbb-dev`; the base's ldd gate whitelists only `libtbb.so`.
4. **Java level chain:** Dropwizard 5.0.2 needs 17; all pom source/targets are <= 11 (prima modules: 11; langident: 11) - they compile cleanly with JDK 17. If an *old Maven plugin* misbehaves on 17 (watch: `maven-checkstyle-plugin 2.17` bound to `validate` in the langident build, `appassembler 2.1.0`), the fallback is `-Dcheckstyle.skip` for that one build step only - flag it, do not do it preemptively.
5. **OpenCV 4.14.0 + gcc 15 + CMake 4.2.3:** low risk (4.14.0 is a 2025 release, CMake floor 3.7, 26.04's CMake is 4.2.3; distros with gcc 15 build this OpenCV). 6. **Qt detection:** `qtbase5-dev` provides the Qt5 CMake config files OpenCV needs. If OpenCV's configure prints `Qt ... NO` and highgui is required, add `qt5-qmake` to the base install list.
7. **Stale-copy nesting** in `buildImage.sh` (fixed in Step 7): if the tooling build ever fails with missing modules, check `ls docker/docker.loghi-tooling/` for a nested `loghi-tooling/` dir first.

9. **Network:** builds need apt 26.04 repos, GitHub (opencv + langident clones), Maven Central, and `maven.huygens.knaw.nl` (algomas-core for langident) - same as today, no new dependencies.

## 7. Questions and ambiguities (defaults chosen)

1. **Java version for the tooling image** - A: **openjdk-17 (default)**: satisfies Dropwizard 5.0.2's minimum, compiles all source/target 11 poms, minimal behavior change.

3. **OpenCV version** - A: **keep 4.14.0 (default)**: already built into the current base (uncommitted script bump); tooling references get aligned up.

5. **Runtime-lib placement** - A: **keep current split (default)**: base keeps runtimes it kept before, tooling installs the critical ones explicitly (+`libavutil60`/`libswresample6` as insurance).
